# 요구사항 해석 및 개선 의견

## 1. 요구사항 해석

이 과제에서는 원 비즈니스 시스템이 아니라 `알림 시스템 자체`를 구현하는 것으로 해석했습니다.

즉, 수강 신청이나 결제 같은 이벤트는 이미 외부에서 발생했다고 가정하고, 이 시스템은 아래 역할만 담당합니다.

- 알림 요청 접수
- 영속 저장
- 비동기 발송
- 재시도 / 최종 실패 처리
- 상태 조회

핵심 해석은 다음과 같습니다.

- `중복 발송 방지`
  - 동일 이벤트를 같은 사용자 / 같은 채널에 여러 번 저장하지 않도록 DB unique 제약을 진실원천으로 사용
- `비즈니스 트랜잭션에 영향 없음`
  - API는 저장만 하고 즉시 반환
  - 발송 실패는 워커가 흡수하고 이력으로 남김
- `운영 전환 가능한 구조`
  - 메시지 브로커 없이도 DB 기반으로 재처리 가능
  - 향후 브로커 도입 시 핵심 상태 머신과 재시도 정책은 유지 가능
- `운영 시나리오 대응`
  - 단순 성공/실패 외에 stuck row, stale worker, 수동 재시도까지 포함해 다룸

---

## 2. 현재 설계에서 의도적으로 선택한 것

### DB에 저장하고 워커가 처리하는 구조

과제 범위에서는 메시지 브로커까지 도입하는 것보다, 알림 요청을 DB에 저장하고 워커가 처리하는 구조가 더 단순하고 검증 가능하다고 판단했습니다.

이 선택으로 얻은 점:

- 구현 범위 대비 높은 완성도
- 상태 조회와 재시도 정책 설명이 쉬움
- 서버 재시작 시 자연스럽게 재처리 가능

### at-least-once 전달 보장

현재 구현은 `exactly-once`를 주장하지 않습니다.  
외부 발송 성공 이후 DB 반영 실패 윈도우가 남아 있으므로, README에도 이 한계를 명시했습니다.

과제 범위에서는 이 한계를 숨기기보다, 어디에서 중복 가능성이 남는지 정확히 설명하는 편이 더 중요하다고 판단했습니다.

## 3. 개선하고 싶은 점

### 1) 외부 채널 idempotency key

운영 환경에서는 외부 채널이 같은 요청을 dedup할 수 있어야 합니다.  
예를 들어 `notification.id`를 외부 발송 요청의 idempotency key로 사용하면 `send 성공 / recordSuccess 실패` 구간의 중복을 줄일 수 있습니다.

예시 방향:

```java
public interface NotificationSender {
    NotificationChannel supports();
    void send(Notification notification, RenderedNotification rendered, String idempotencyKey);
}
```

### 2) timeout / circuit breaker

현재 sender는 mock라서 단순하지만, 실제 외부 채널 연동 시에는 timeout과 circuit breaker가 필요합니다.

이유:

- 외부 시스템 hang이 워커 스레드를 오래 점유할 수 있음
- 특정 채널 장애가 다른 채널 처리량까지 떨어뜨릴 수 있음

### 3) 예외 분류

현재는 대부분의 예외를 동일하게 재시도합니다.  
하지만 아래는 재시도해도 회복 가능성이 낮습니다.

- payload 필수 키 누락
- 지원하지 않는 채널
- 템플릿 자체 오류

이런 경우는 `PermanentException`으로 분리해 즉시 `DEAD_LETTER`로 보내는 편이 낫습니다.

### 4) DEAD_LETTER 운영 정책

현재 `DEAD_LETTER`는 보관만 됩니다.  
운영 환경에서는 다음이 필요합니다.

- 보관 기간
- archive 정책
- 운영자 알림
- 수동 재처리 이력 관리

### 5) 메트릭과 모니터링

실운영에서는 다음 지표를 수집하고 싶습니다.

- 채널별 성공 / 실패율
- 재시도 비율
- `DEAD_LETTER` 누적 수
- 평균 발송 지연 시간

이번 과제에서는 핵심 평가 포인트가 멱등성, 재시도, 복구라고 판단해 관측성은 문서 수준의 개선 항목으로 남겼습니다.

## 4. 면접에서 설명하고 싶은 포인트

이 구현에서 강조하고 싶은 부분은 3가지입니다.

1. `DB unique constraint`를 멱등성의 진실원천으로 삼았다는 점
2. 외부 발송을 트랜잭션 밖으로 빼서 장애 전파를 줄였다는 점
3. `SKIP LOCKED + worker_id + stuck recovery` 조합으로 다중 워커와 운영 복구를 다뤘다는 점

반대로, 현재 한계도 명확히 설명할 수 있어야 한다고 생각합니다.

- exactly-once는 아님
- 외부 채널 idempotency key가 아직 없음
- timeout / resilience layer는 아직 문서 수준 제안에 머물러 있음
